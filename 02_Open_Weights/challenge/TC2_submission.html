Week 2 of the project, told as it happened

The fake contracts were clean.
They were also all the same.

Two generation runs, 50 cases read by hand, two review sessions with the sponsor.

The need. My agent helps contract owners act before renewal deadlines. To test it, I need hundreds of contract cases, and real contracts cannot leave the company.
The trick. I described how real cases differ (urgency, complexity, missing information) and asked a model to invent cases, starting from 9 examples I wrote by hand.
The surprise. First run:0 refusalsNo case where the agent must refuse to draft. The model had never seen such an example, so it invented its own labels, and my checks threw them all away.
The lesson. I read 50 cases: they sounded alike. Then the sponsor, who handles these contracts every year, showed me what was missing.

The fake data proved my pipeline works.
Only someone who handles real contracts could tell me what it cannot prove.

This page follows that path: how the cases were made, what survived the checks, what I found when I read them, and what they must never be used to prove.

01 Variation axes

Axes: two domain-specific, one refusal

Three ways real contract cases differ, and one value where the agent must refuse

To invent useful cases, you first say how real cases differ. Each way is an "axis" with a few values. The model then invents cases for every combination of values.

From my notes

My agent does not read free text. It receives six fields: the owner's decision (renew or terminate), three dates, whether the owner is still in the company, and whether the signed contract is on file. So my axes describe the contract's situation: how urgently the contract must be managed, how complex it is, and what information is missing.

A refusal (the course calls it a "decline") is a case where the agent must not draft anything, for example when the signed contract cannot be found.

Axis and its valuesReason
time_left
  1. more than 30 days before the deadline (auto-renewal date if one exists, otherwise end date): comfortable
  2. 14 to 30 days left: the owner must answer now
  3. less than 14 days left: not enough time for the internal purchase request and order
Time left decides the tone, the recipient, and whether the purchase process can still finish (it needs about 2 weeks)
contract_complexity
  1. simple: per-user or per-usage subscription, one price line
  2. complex: priced on compute capacity, plus license and support fees, so the quantity is hard to estimate
  3. very complex: several cloud instances, each with its own users and third-party add-ons, plus a paid security support line where the vendor's responsibility in incidents matters
Stakes and review depth grow with the number of price lines and the security risk
record_completeness
  1. nothing missing: owner active, signed file found
  2. partly missing: the owner has left, signed file found
  3. Refusal critical missing (decline): signed contract file not found
Missing information changes who gets the message, and some gaps block drafting
After the sponsor review (for the next run, not used to generate this data): complex and very complex contracts involve several departments, which must provide last year's usage and next year's forecast before a quote can be requested. Very complex also covers products used by internal users and customers at once. Support and security are two separate paid add-ons, not one "security support line".
A case I had to think through

The owner has left the company, but the signed contract is on file. Should the agent draft the letter anyway and send it to procurement (the purchasing team)? No: procurement can check the letter, but only someone in the team can say whether the product is still needed. So the decision is reviewed again before anything is drafted.

02 Generate, dedupe, validate

Four counts and settings

162 invented, 128 kept, and the first run had no refusal cases at all

Every invented case goes through two filters: near-copies are removed (dedupe), then each case is checked against the exact format the agent accepts and returns (the schema). What survives both is the honest size of the dataset. A "dead combination" would be a mix of axis values that produced nothing.

Run 1 finding: no decline or escalation row survived validation. The prompt showed only goldens 1 to 3, so the model never saw missing_file_notice, escalation_to_procurement or owner_status: "left", and it invented its own names and values. Run 2 shows goldens 1 to 6, which cover all five message types: 2 rows rejected (invented decision value).

What I saw in the rejected cases

My agent has five fixed message types, such as "termination draft" or "missing file notice". In run 1 the model had seen only three of them, so it invented five different labels for "I cannot draft this": missing_file_block, decline_missing_file, blocked_missing_contract, and two more. All sensible, none of them in my format, so the check threw all of them away. Without that count, I would have believed my data tested refusals.

Settings, so the run can be reproduced

Temperature: not set in either run (Anthropic default 1.0, looked up). Top-p: not set (provider default, about 0.99, looked up)

Dedupe: character 4-gram Jaccard on input, threshold 0.9 (reasons in decisions.md)

Validator: pydantic model with input: Request, output: Response, why: str, imported from 01_Product_Engineering/challenge/schema.py

03 Dedupe threshold

Decision row: dedupe threshold

At the default setting, cases with different dates looked like copies

Dedupe compares two cases character by character and drops one if they overlap more than a threshold (0.7 means 70% the same). The right threshold depends on what the data looks like.

From my notes

In run 1, at the course default, dedupe threw away 61 of 81 cases. They were not copies: only the dates differed. Every case starts with the same field names, and to a character counter, that looks like the same text. A person reads "renew" and "terminate" as two different cases; the counter sees one word out of 150 characters.

I chose the threshold on run 1 and kept it for run 2: there, it kept 130 of 162 cases.

Decision: Dedupe threshold 0.9 on character 4-grams of the input field. Chosen on run 1 (81 rows: kept 75), then applied to run 2 (162 rows: kept 130)

Rejected: 0.7, the session default (run 1: kept 20 of 81: it dropped rows with different dates, because the dict keys are the same in every row). 0.95 (run 1: kept 78 of 81: the same wrong drop, and fewer real duplicates removed). Not re-tested on run 2: its raw rows were not saved

Why: Inputs are short structured dicts: most characters are field names, so character overlap is high even when the content differs. 0.9 removed the near-identical rows and kept rows with different dates. Known limit, seen in run 1: at 0.9 and 0.95 one renew row was dropped as a twin of a terminate row, because a one-word change is too small for character overlap to see. In run 2, the 5 dropped pairs I checked had the same decision and near-identical inputs (one differed by one day)

What would change my mind: More dropped pairs that differ in decision, owner_status or file_exists. Then dedupe on exact field values (decision, owner status, file status, time zone) instead of character overlap

04 Leak check, then fifty cases read

Leak check and fifty rows read

Nothing leaked, but almost everything repeated

Before anything is published, two checks: an automatic search for real names and numbers copied from my examples, then my own reading of 50 random cases.

The automatic check

It only flagged the invented dates from my own examples and a generic greeting. No names, no identifiers: the examples were written from memory, with placeholders such as [Product] and [Owner].

My reading

50 random cases, read one by one: for leaks first, then for sense. No case removed. What I found was not a leak. It was sameness.
From my reading notes

"I do not have the feeling that this synthetic data made the dataset richer. I really do not see much variety." The complexity axis never reached the renewal emails: they always ask the same four questions (duration, licence model, quantity, usage), because my agent does not read the contract yet.

Read by me: 50 random valid rows (sample seed 7). Removed: none. Looked for: real product or vendor names, internal formats, copied rare cases, and claims the agent cannot know.

Low variety: messages stay close to the goldens' wording. Renew messages always list the same four review points from golden 2, whatever the contract complexity. Missing-file notices are nearly identical whatever the time left.

Complexity reaches the message only through the axis text, never through the contract, because the agent does not read the file. Reading the file comes with retrieval (Week 3).

Dedupe compares inputs only, so rows with different dates but near-identical messages were all kept.

Value of this data: coverage of input situations (decision, dates, owner, file) with the expected type and act_by, for routing tests. Not message variety.

The four outward checks, ticked by me

✓ No real record was used as a seed.
✓ No real entity names, IDs, or identifiers appear.
✓ No distinctive internal formats that would identify the firm.
✓ Rare categories were generated, not copied.

Expert check (Oct 16): if this were public, the sensitive parts would be amounts and the technology stack, because knowing which tools we use shows an attacker where to aim. The rows contain no amounts, and the product and add-on names are invented, so they do not describe our stack.

05 The datasheet

Cannot validate · never compared against · goldens disjoint

It proves the pipeline works, not that the agent writes well

A datasheet is the label on the data: where it comes from, what it may be used for, and what it must never be used to prove. In six weeks, people will read this page instead of the data.

What this data is

This is prototyping data: inputs that look like real renewal cases, with no labels a person verified.

What it can validate

The pipeline runs end to end: generate, dedupe, validate.

The generated inputs fit the current Request schema, for each combination of time_left and record_completeness.

The validator rejects rows that do not fit, and the counts show how many.

Routing coverage: 128 input situations (decision, dates, owner status, file status), each with the type and act_by the model chose, to test routing in Week 4. Not message quality.

Plausibility, narrowly: the contract owner read 14 rows and found no situation that would never happen ("we are covered at 99%"). That is one expert on 14 rows, not a measure of the whole file.

What it cannot validate

Message variety and writing quality: messages are close paraphrases of the goldens.

Deadlines set by the vendor: an early-renewal price deadline can arrive weeks before the end date, so time_left from the database can be wrong (expert review, Oct 16).

Real complexity: the expert defines it by how many business units must approve, and whether the product serves internal users and customers at once. It is often discovered only at the first quote. None of this is in the schema or the data.

Realistic contract wording: the axis value "paid security support line" is something the expert has never seen in a contract. Real contracts have two separate paid options: a software support add-on and a security add-on.

Six more limits

Dedupe uses character overlap, which cannot see a one-word change in a structured field: one renew row was dropped as a twin of a terminate row in run 1.

Validation checks types and allowed values only: not that dates are consistent, that act_by is right, or that the message matches the decision.

Which message types appear depends on which goldens the prompt shows: with 3 seeds, run 1 produced zero decline rows.

With less than 14 days left, the model wanted an urgent-warning message type the schema does not have. Urgency exists only in the message text.

Rows reuse the goldens' invented dates (2026-10-12, 2026-11-15, 2026-12-15), so date variety is lower than it looks.

A missing vendor contact: when the vendor's people change and the new email is not in our files, the process blocks. No row covers it. It matters in a later step, after the owner has reviewed the contract.

What it must never be compared against

Real ground truth is the real contracts and what contract owners actually decided and sent: the contract database and the project mailbox, inside the company's private system. These synthetic rows are not ground truth: their labels (message type, act_by, message) were written by the generating model and checked by no one. A masked copy of real contracts may become a backtesting set later, in the private company repo, never in this public fork.

Are the goldens disjoint from anything the system was tuned on?

The "goldens" are my 9 hand-written test cases, each with the answer I accept. They are the exam the agent is scored on, so the agent must never learn from them or from anything copied from them.

No: overlap. The goldens were written from memory, not from real contracts, but in TC1 the drafting prompt for each message type was adjusted until the goldens passed. A passing score on the goldens partly measures that tuning, not correctness on new cases. This file was generated from goldens 1 to 6, so it must never be used to tune anything the goldens later score: no prompt examples, no fine-tuning.

Overlap by the dedupe measure: 122 of 128 rows within 0.5 of a golden. The number is inflated: every row shares the same field names, due to my input data structure, so it does not mean the content was copied.

06 Model and endpoint

Model/endpoint row: measured vs looked up, constraint vs preference

Hosted for fake data now; real contracts wait for an approved route

Which AI model wrote the cases, and which one could run on real contracts later: a hosted model (the provider runs it, data leaves the network) or a local one (it runs on our own machine). Every number below is marked "measured" (I timed it) or "looked up" (from a price page).

15 slocal 350M model on my laptop CPU, 80 tokens (measured)
3.8 shosted model, same prompt and budget (measured)
≈ $0.001for that call: tokens measured × price looked up
From my notes

The small local model wrote "the database database" and "restaurant restaurant". Fast enough for a daily job, not good enough to write a letter to a vendor. The sponsor's view, when I showed both: "why deprive ourselves of a smart model?" (translated from French)

Decision: Model/endpoint: TC2 synthetic data on hosted anthropic/claude-sonnet-4-6 (Anthropic API). Real contracts: a capable hosted model, once a route is approved

Rejected: Local LiquidAI/LFM2.5-350M on my laptop CPU. A local model on the pilot VM

Why: Measured on the S3 Task 9 fixed prompt ("The incident started when the database"; the hosted model also gets a one-line "continue the text" system instruction), 80-token budget: local LFM2.5-350M on Intel Core Ultra 5 335 (8 threads, 15 GiB RAM in WSL, CPU only) 15.13 s, with doubled words; hosted claude-sonnet-4-6 3.79 s, 58 in / 71 out tokens (measured). Price $3 / $15 per million input / output tokens (looked up, Oct 16 2026), so this call cost about $0.001 (computed from both). There is no approved LLM route yet: this is the first system of its kind at company level, so no one has asked for one. Until a route is approved, real contract data does not go to a hosted API (constraint, until approval). TC2 rows are synthetic with invented names, so they may go (constraint met). The agent must follow instructions and return the schema fields, and the 350M model cannot (constraint). A local model needs a vendor review first (security certification, third-party risk review), and this one's licence becomes paid above a company revenue threshold (constraint, expert review Oct 16). Faster replies (preference: the agent runs as a daily job, so 15 s is fine)

What would change my mind: The route is approved: use it for real contracts. A similar AI integration with read-only access is already approved, which the request can build on. Anthropic now marks Sonnet 4.6 as legacy: re-run the goldens on its replacement before switching

07 Shown to someone who knows the real data

Demo to a real user, feedback in my own words

"We are covered at 99%." The 1% taught me the most

Invented cases only look real. The course asks to show them to someone who sees the real ones every day, and to ask three questions in a fixed order.

How it went

My reviewer was the Head of IT infrastructure: the sponsor of this project, who owns about 80 to 100 contracts and renews them himself. Two screen-shares on the same day: about 50 minutes, then 35. I showed 14 cases, not 20. The others were near-copies, and he noticed it himself: "it's a copy of what you showed me before" (translated from French).

The moment that changed my time_left axis

The database said three months. Then the vendor wrote: renew within days, or the price goes up by about 8%. The real time left was two days.

QuestionWhat he said, in my words
Which of these would never happen?none. Every situation shown happens often (owner left and escalation, accept or refuse to continue, renegotiating a bundle): "we are covered at 99%". He first doubted a "terminate" decision on record when the owner has left, then agreed it happens: the owner had noted in advance that the contract would not be renewed. One wording never happens: "a paid security support line" does not exist in contracts; real contracts have a separate support add-on and security add-on.
What comes in that is not here at all?a vendor whose contact people changed, with no new email in our files, which blocks the process; a deadline set by the vendor (an early-renewal price deadline before the end date, so the real time left is shorter than the database says); complexity defined by how many business units must approve and by internal plus customer use; complexity often found only at the first quote (bundled licences, a big price increase); the vendor's fiscal year as a pricing lever (not V1); tools bought without approval by people who then left; termination prerequisites (equipment return, decommission, data backup).
If this were public, what would worry you?amounts and the technology stack: knowing which tools we use shows an attacker where to aim. The risk stays limited because access is already well protected.

What his feedback changed

Expert feedback (Oct 16): redefine contract_complexity for the next generation run: very complex = several business units must approve, or internal users and customers at once; complex = the vendor changed its licence model or bundles, often seen only at the first quote; both involve several departments, which must provide last year's usage and next year's forecast. Replace "a paid security support line" with two separate paid options: a software support add-on and a security add-on

Message changes he asked for, saved for the Week 4 goldens

escalation text "I can't start the review until an owner is assigned"; termination draft cites the notice period and asks for next steps (equipment return, decommission, data backup); review email offers "one year, three years, or both" and asks for the forecast; auto-renewal is never wanted; missing-file notice adds "if you do not have the contract, ask the vendor for the last signed copy"; when the decision is terminate, no complexity detail in the message; escalation asks for a new owner and says a new review cycle starts if the new owner does not terminate; review email asks per cloud instance whether it is still needed and which add-ons can be dropped; new case to cover: the vendor contact changed and the new email is unknown

My favourite tip

When nobody can find the signed contract, people go to legal, to finance, to the person who left. His answer: "ask the vendor". They always have it, and it is the shortcut that stops a case from sleeping for years.
