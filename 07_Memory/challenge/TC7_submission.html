Contract Agent · Week 7 · memory

My agent read the whole contract every time someone asked when it ends.

The contract agent helps contract owners renew or end contracts on time. My sponsor, the Head of IT infrastructure, owns about 80 to 100 contracts. Until this week, every question started from zero: the agent searched the documents again, 2 to 5 times, even for a date it had read yesterday.

What it costs

Every search is a tool call, and every call resends the whole conversation to the AI model. Simple questions paid the most for the least.

What memory can break

A stored fact can be old (the contract was renewed), from the wrong contract, or shown to the wrong person. A wrong fact said with confidence is worse than no fact.

This week's question

Can the agent remember each contract's key facts, answer from them, and prove the memory is current, cheaper, honest and private?

00 AI Forward-Deployed Engineer · Technical Challenge 7

Memory

I gave the contract agent one kind of memory: a record of each contract's key facts, each with the document section it came from. A newer document replaces the old record. I tested it four ways: it stays current, it is cheaper, its account of what it did matches the log, and no one sees another owner's contracts. Then I checked it on my Week 4 questions: quality held after one fix the tests found. All contracts, vendors and prices are invented. Roles, not names.

Two rules the database enforces

Only one live record per contract: a renewal turns the old record into history, it is never deleted. Every fact has a source line, so every answer can cite where it comes from.

Part 1: three kinds of memory, one chosen

Three kinds of memory. Only one moves my sponsor's first goal.

Chosen

Semantic: what is true now

For us: each contract's end date, notice period, renewal type and value.

It would control: the renewal alert, and quick answers ("when does it end?").

Later

Episodic: what happened

For us: past negotiations, what was decided at the last renewal, the discount we got.

It would control: negotiation prep and the "saved money" measure.

Needs real history. The synthetic contracts have none.

Later

Procedural: how we do things

For us: how each owner prepares a purchase order (which account to charge, a prepaid licence split by month), the email style each owner likes.

It would control: correct purchase orders, even after an owner hands a contract over.

Approvals stay in the company's finance and purchasing system (sponsor, Nov 24). Needs real renewals to learn from.

Why semantic

The charter's first measure is alerts 100% on time. An alert needs a saved, correct end date and notice period. This record is the stepping stone: record, then alert, then better answers.

Part 1: one kind of memory, and why

My choice and what I rejected, word for word from my decision log:

Memory (Nov 20): semantic memory = the contract record (end date, notice period, renewal type, owner, vendor, product), in the same SQLite store the alert needs (Week 5 next-build row). One store, not two. Record fields are written only when a contract document arrives, with that document as their source. Conversation notes go in a separate table, with date and source, and never replace a record field. Vendor and product names, security products included, are stored (synthetic here)

SQLite: a database in one file. The alert: the reminder sent to an owner before a decision deadline (planned).

Rejected

Episodic memory (decision history, negotiation history, relationship with the vendor). Procedural memory (internal policies, email style per owner). A separate memory store next to the contract database

Why

The record is what the alert and most questions need, so most answers come from the record, and document search stays for specific terms. Documents are the ground truth: a fact taken from a chat can be wrong and still sound right. One store: the alert and the agent read the same live value, so they cannot disagree. Episodic: the synthetic data has no real history yet. Procedural: the policies are rules people write, not something the agent learns, and there is no repeated work to learn from yet. Names: the alert needs vendor and product anyway, so leaving them out of memory protects nothing; protection comes from the vendor and owner filters and from access to the store
The sponsor's view, Nov 24

Approvals stay in the company's finance and purchasing system, so the agent should not rebuild them. Procedural memory still has a real use: each owner's rules for preparing a purchase order, which are lost today when an owner leaves. That keeps it for later, with a clearer target.

Part 2 and test 1: staleness, supersede on write

A renewal replaces the old record; the old one stays as history

Contracts get renewed, so a stored end date goes out of date. Of the three ways the course names (recency, supersede, validity windows), I use supersede on write (a new document replaces the old record when it is saved): the save function marks the old record as history and writes the new one as the only live record, in one step.

The test

Save Vendor10's first order form (ends 30 November 2026), then its renewal (ends 30 November 2027). The live record must be the renewal, and the first order must still exist as history.
1 passedwith the rule on
1 failedwith the rule switched off: the database refuses a second live record
Why supersede, at the record level

A new document starts a new term, so the old record's dates belong to a term that is over. An alert on them makes no sense, and an owner who never answers must not leave the alert on dead dates. The old record is kept, not deleted, so the history of the contract stays.

Why tokens fall less than calls

Every model turn resends the instructions and the tool list, and the memory tool's description adds about 650 tokens to every question, even one it cannot answer (the control went up). An answer from memory still takes 2 model turns: one to call the tool, one to answer.

One more thing the logs showed

Why it matters

If the story says "I read the pricing section" and it did not, the owner trusts a source no one read.

Fails on

A tool named but never called. A section cited but never returned. No story at all. A tool used but not named is only a warning.

Part 3, test 3: truthfulness

This is the sponsor's audit question, "why did it say this?". The agent ends each answer with two fixed lines, TOOLS USED and SECTIONS READ. Code compares them with the trace (the log my code writes while the agent works), never with the model's own words. The same 5 questions as test 2, memory on, 1 run each.

Truthfulness test (Nov 22): one turn. Each question carries the request to explain: the agent ends its answer with a TOOLS USED line and the sections it read, and truthfulness.py compares them with the trace run_agent logged. Fails on: a tool named but never called, a section cited but never returned, no TOOLS USED line. Warns, does not fail, on a tool called but not named

run_agent: the agent loop in my code. Trace: its log of each tool call and the sections returned.

Break check, no model

test_truthfulness.py: a fake log and two fake answers. The true one passes; one that names a search never run and a section never returned fails. With the check switched off, the test fails: 1 failed, 1 passed.

Limits

One turn: the agent explains while its tool results are still in view, so a pass proves less than a real audit days later. One run per question, so a rare false claim could slip through.

Who sees what

An owner: their own contracts. Procurement, legal, admin, CIO, CFO, CEO: all (finance removed after the sponsor review, Nov 24). Unknown: nothing, and is told to contact procurement or the admin. 6 tests, no AI call; each fails when I break the rule.

The leak the test caught: a fake bug, a real risk

"Contract 2 of Vendor04" returned Vendor02's record: the lookup took the first number. That exact bug comes from my numbered fake names. The real version: someone's words map to the wrong contract (one vendor, three contracts; names with numbers in them). Fixed and tested here; for real contracts it is why each contract needs an id we create.
Part 3: the leakage test, because my app has users

The scope comes from the sponsor (Nov 18): each owner sees only their contracts, the CIO sees all. The course app has no login yet, so the owners are invented roles ("owner 1" to "owner 3") assigned to the 10 synthetic contracts. The filter lives in the store and in the tools the agent gets, not in the prompt: whatever the AI does, it cannot reach a record or a document outside the viewer's contracts.

Is the leak real?

The exact bug (taking the first number in "contract 2 of Vendor04") needs numbered vendor names, which only my synthetic data has. The kind of failure is real: the lookup turns a person's words into a contract key, and real names are messy (one vendor with several contracts, product names with numbers, near-identical names). Real contracts carry no id, so the next build creates one per contract and matches each document to it, asking a person when unsure.

Limits, written down

Until login exists, my tests and the demo page run as the CIO, so they do not use the owner filter end to end. The MCP server (the tool server for Claude Desktop) stays unfiltered: a local developer tool. Owners come from a hand-written list, not the contract database.

The leak I may want

When someone starts buying a product, should the system tell them the company already has a contract with that vendor under another owner? It would avoid a duplicate purchase, and it crosses the line this test protects. My leaning: show only "exists, owner role X", no dates or price. Open, for the sponsor.

Bug: the missing unit

Right record, current value, but "30" without "days". The agent doubted it and the judge flagged it. Fixed with one word in the field's label.

Gap: the notice deadline

The record holds the notice period, not the last day to give notice. A one-call answer sometimes leaves the deadline out. Next build: code computes the deadline and stores it.

Noise

Each run fails one different question. The last one asks about two vendors and nothing in the record, so it takes the same path with or without memory.
Wrong entry or old entry?

The course asks which of the two a memory failure is: retrieval (the wrong entry) or staleness (the right entry, out of date). The missing unit was neither: the right, current entry, used badly because it was stored badly. The wrong-contract lookup was retrieval, caught by the leakage test, not by these scores.
