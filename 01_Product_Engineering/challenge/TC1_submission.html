A true story, names removed

The dragon
never negotiates.

As told by our Head of IT infrastructure.

One of our software contracts says it clearly: if the purchase order is not in before the end date, the price goes up 15%, automatically. The clause was known. It just had no one acting on it.
The vendor is a dragon in negotiation. When the contract says it, they apply it. No discussion, no exceptions.
Last year the purchase order arrived late. The date lived in a shared spreadsheet, checked on a call every two weeks. Nobody saw it coming.
The price went up 15%, for the same product.a penaltylost in one day, for nothing.

The money was not lost in the negotiation.
It was lost on a date nobody was watching.

This project is about those dates: notice deadlines, end dates, the last day to say no. And this is not one bad day: about 1 in 5 renewals are late or missed.

Problem sentence

The problem in one sentence

Contract owners act too late on renewal notice deadlines, with about 1 in 5 renewals late or missed, because tracking is a manual spreadsheet reviewed on a call every two weeks, which costs about 120 person-hours per year across the team.

Who: Contract owner. They are multiple within the company (usually head of every department). Particularly here Head of IT Infrastructure that owns today about 80-100 contracts.

Today: A shared spreadsheet, a review call every two weeks, manual emails, and a manual update at the end.

Success: Alerts 100% in time; renewals on time about 80% to 95% (e.g. no penalties for late renewal); review meetings about 26 to 4 per year.

03 Agent or pipeline

Agent-or-pipeline verdict

Pipeline: a function, not an agent (0 of 4 questions true)

Q1: No. Every contract goes through the same steps. A different number of review points per contract changes the size of the output, not the steps.

Q2: closest call: current SaaS terms on the vendor website would need a fetch, but that is one fixed step, not an agent. The rule for which contracts trigger it is written in code.

Q3: No. Every draft goes to the owner for review before anything is sent, and the failure cases (deadline passed, contract missing, owner left) route to a person instead of retrying.

Q4: No. The input is always a contract and the owner's decision, from a closed set: terminate or renew.

Rejected

An agent.

Strongest case for the opposite verdict

I would switch to an agent if, over 1 year, owners approve the proposed drafts without edits in at least 90% of cases, and the next step keeps depending on the vendor’s reply. Then the human check adds cost without value, and a fixed pipeline cannot follow the negotiation.

05 The endpoint

Four endpoint questions

draft_message_for_renew_or_terminate

1. What is one thing you do at work this could take over?
Today: a shared spreadsheet, a review call every two weeks, manual emails, and reminding myself to check where I am with each contract. This endpoint takes over one step only: writing the next message after the owner says renew or terminate. That can be the notice to the vendor, the review email for the current contract, the request for a missing contract file, or the escalation to procurement. Why it matters: about 120 person-hours a year in review meetings, and about 1 in 5 renewals late or missed.

2. What exactly goes in?
Six fields, not a file or free text: decision, autorenew_date, end_date, today, owner_status, file_exists. Dates are text in YYYY-MM-DD format; an empty autorenew_date means no auto-renewal clause; file_exists is true or false. The contract file itself is not read: file_exists only says whether it is on record.

3. What comes back, and who reads it?
One text with message_type, act_by and message. Who reads it depends on the type: termination_draft: the owner reviews it, then sends it to the vendor. late_notice_to_owner, renewal_review_email, missing_file_notice: the owner. escalation_to_procurement: procurement. act_by gives the reader the last day to act. The app sends nothing.

4. What did you name it, and why would an agent pick it correctly?
draft_message_for_renew_or_terminate. "draft": it writes and sends nothing, so it is different from a tool that approves or sends. "renew_or_terminate": the draft depends on the owner's decision, renew or terminate, so the name names both and nobody reads it as "only for renew". Not "owner_decision": later owner decisions (price, retained quote) would fit that name too. The name says draft and the docstring says it sends nothing, so an agent will not call it to send a message.

Other endpoints in the app: show_prompt_for_renew_or_terminate (shows the prompt, no model call) and chat (raw model, not the agent).

07 Containerized

CDN paragraph

Runs in Docker; one silent dependency on a public CDN

frontend/index.html imports the Gradio client (@gradio/client) from a public CDN, cdn.jsdelivr.net. The browser makes this request, not the container, so what matters is the user’s network. If that network blocks the CDN, the page still loads and shows the date and the model, but the form does nothing and shows no error. My two probe runs (use_case/ecosystem.md) reached jsDelivr, but both ran from my home network, not from the office or the deployment VM. The fix is to vendor the library: download a pinned version at build time, copy it into the image, and serve it from the app. Then the browser never calls the CDN at run time. The URL also has no version, so pinning it fixes the same problem uv.lock fixes for Python packages.

Image vs virtual environment

A virtual environment holds only the Python packages; the image also holds the operating system, the Python version, the code files, the user it runs as, the port and the start command. So a platform team can run the image with no setup and no guessing: they only add the keys at run time, and if a file is missing (like schema.py was in my first build), it fails the same way for them as for me.

Cloud providerAzure, US region.
AuthenticationEntra ID. Pilot users connect from Claude Desktop over the corporate network; inbound 443 is open from the corporate network only, never from the internet.
External LLM API?The network, yes: outbound 443 to the model API is in the allowlist ticket IT is opening. The approval, no: there is no approved internal LLM, no Azure OpenAI instance and no approved Anthropic API (Oct 12). So in production it can use no model until a route is approved. What changes to deploy?The code stays the same; how it runs changes: model route (config only); secrets by the method the IT SOC team approves, not --env-file; image built on the VM or pulled from a private Docker Hub repository; Gradio client served from the image, not the public CDN; Entra ID login in front of real users; internal DNS name and TLS certificate for 443.

09 Vibe check

Vibe check, aspect named for every prompt

Code gets the type right; the model can still say something false

Pass 1 · general capability

Five prompts in the raw Chat box. Correct answers, but heavy markdown and extra content in all five, even with "Be concise". My rules must override that default.

Pass 2 · my use case

message_type and act_by matched the golden in every run, because code decides them. No markdown, placeholders kept, "may not" instead of "does not". One small invention in golden 4.

Pass 3 · where it falls down

Two experiments that try to break it: owner left with no auto-renewal (A), contract already ended (B).

Pass 3, Experiment B: contract already ended

Aspect tested: invalid input: no check that the dates make sense. Inputs: terminate, no auto-renewal, end date 2026-09-30, today 2026-10-12.

Subject: [Product]: end of contract on 30 September 2026

Hello [Vendor contact],

We are writing to let you know that our contract for [Product] ended on 30 September 2026 and we will not be continuing after that date. We wanted to inform you in good time so that you can plan accordingly.
...

The model partly noticed the date conflict: it switched to the past tense ("ended", "stopped"). But it still followed the rule "We tell them in good time so they can plan", which is false 12 days after the end date. The draft contradicts itself.

The real limitations of this application (9)

1. No access to my systems. The only input is six fields typed by hand, one contract at a time.

2. No memory. Every run starts fresh: it does not know the owner was already told, or that a reminder was sent.

3. "File found" is only yes/no. The agent never reads the contract.

4. The notice deadline is typed by hand. It should be calculated from the contract: the auto-renewal date minus the notice period in the contract.

5. No urgency. The escalation asks for a new owner whatever the time left (Experiment A).

6. No input checks. An end date in the past is accepted and routed like a normal case (Experiment B).

7. Placeholders only. No real product, vendor or owner names, so every draft needs manual completion.

8. Silent failure on a blocked network. If the CDN for the Gradio client is blocked, the form loads and does nothing.

9. Drafts only (scope). No sending, reminders, escalation follow-up or quote comparison yet.

What a vibe check is worth as evidence

A vibe check is weak evidence: one run per case, judged by eye, so it exposes the system's real limitations and helps plan the roadmap, but it cannot show that one version is better than another. Before comparing two versions, I would write down for each golden what the text must contain (for example the deadline date and the request to the owner) and must not contain (an invented fact, a legal rule stated as fact), then test every version against the same conditions on many goldens built from real contracts.
